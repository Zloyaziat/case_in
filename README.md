# case_in — ИИ-помощник принятия решений для химического производства

Сервер ведёт **партию** (один производственный цикл) по заранее заданной **формуле**: шаг за шагом
принимает показания датчиков, усредняет их по коротким окнам, сравнивает с **эталонными партиями**
и при отклонении выдаёт оператору рекомендацию:

> Нужно увеличить массу лактида до 139.65 кг на датчике D-LAC-04!

Стек: FastAPI + SQLAlchemy (async) + PostgreSQL 17, фронтенд — статические HTML/JS без сборки.

## 1. Быстрый старт

### Одной командой (Docker)

```bash
docker compose up -d --build
```

Через 10–15 секунд:

| Адрес | Что там |
|---|---|
| http://localhost:8000/frontend/batches.html | страница оператора: запуск партии, ход шагов, рекомендации |
| http://localhost:8000/frontend/formulas.html | приёмка формул (загрузка, проверка, расчёт массы) |
| http://localhost:8000/docs | Swagger — все эндпоинты с примерами |
| http://localhost:5050 | pgAdmin (логин/пароль — в `.env.docker`) |

При **первом** старте Postgres сам загружает дамп `sql/case_in.sql` (папка `sql/` смонтирована в
`/docker-entrypoint-initdb.d`). Бэкенд ждёт, пока дамп загрузится, — это обеспечивает healthcheck
с `-h 127.0.0.1`: во время загрузки Postgres слушает только unix-сокет, и проверка не проходит.

Полезные команды:

```bash
docker compose logs -f backend      # логи, в том числе рекомендации по партиям
docker compose down                 # остановить (данные сохраняются)
docker compose down -v              # остановить и УДАЛИТЬ базу; при следующем up дамп загрузится заново
```

> **Дамп грузится только в пустую базу.** Если `sql/case_in.sql` обновился, а volume уже есть,
> новые данные сами не появятся — нужен `docker compose down -v` (удалит все партии!) или ручная загрузка.
> Все файлы в `sql/` выполняются при инициализации по алфавиту — не кладите туда черновики.

### Локально (для разработки, с `--reload`)

```bash
docker compose up -d postgres                 # только база, порт 5433 (см. .env)

python -m venv .venv
source .venv/bin/activate                     # Windows: .venv\Scripts\activate
pip install -r requirements.txt

uvicorn app.main:app --reload
```

Нужен Python 3.13 (как в `Dockerfile`). Строка подключения берётся из `.env`
(`postgresql+asyncpg://postgres:postgres@localhost:5433/case_in`). Переменные окружения
перекрывают `.env`.

### Первая партия за минуту

1. Откройте http://localhost:8000/frontend/batches.html.
2. Выберите формулу **«15: Мел»** — поля сырья заполнятся из первого шага формулы.
3. Поставьте ускорение `×10` и нажмите «Создать партию и запустить».
4. Через 3 секунды все три шага пройдены, ниже — две рекомендации (они специально заложены в файл эмулятора).
5. Введите `v_finish` и качество, нажмите «Завершить партию».

  formulas.html, js/formulas.js   приёмка формул

  opc_formula15.txt       показания для эмулятора OPC (формула 15)
  sensor_data_5000.csv    показания для модуля monitoring

с часами и базой, `routers/batches.py` — с HTTP.

## 3. Партия: от выбора формулы до завершения

```
Оператор выбирает формулу ─► POST /api/batches                   batch.status = created
Вводит сырьё (v_in)       ─► PUT  /api/batches/{id}/v_in          batch.v_in
Нажимает «Старт»          ─► POST /api/batches/{id}/start         batch.status = running, started_at = now
                                                                  batch_step(шаг 1).started_at = now
  ┌── каждый тик (0.1 с) ─────────────────────────────────────────────────────────┐
  │ берём из txt строки, "пришедшие" к этому моменту (эмулятор OPC)               │
  │ t = время строки − начало текущего шага                                       │
  │ показание датчика этого шага → в буфер окна                                   │
  │ окно закрылось → средние → batch_step_window (time = правая граница окна)     │
  │                 сравнение с эталоном → batch_recommendations                  │
  │ время шага вышло (formula_steps.amount_time) → следующий шаг, его started_at  │
  └───────────────────────────────────────────────────────────────────────────────┘
Все шаги пройдены          ─► batch.current_step = NULL   (phase = awaiting_finish)
Вводит v_finish, качество  ─► POST /api/batches/{id}/finish  batch.status = finished,
                                                             finished_at, t_total_sec, is_reference
```

### Статусы

`batch.status` хранится в БД (ограничение `batch_status_check`). Для удобства API дополнительно
отдаёт вычисляемое поле `phase`:

| status | phase | смысл |
|---|---|---|
| created | created | партия создана, можно вводить `v_in` |
| running | running | идёт шаг `current_step` |
| running | awaiting_finish | все шаги пройдены, ждём `v_finish` и качество |
| finished | finished | закрыта; может быть эталонной |
| aborted | aborted | прервана оператором |

### Что может оператор во время партии

| Действие | Эндпоинт | Что происходит |
|---|---|---|
| Закончить шаг досрочно | `POST /{id}/next-step` | текущее окно закрывается с фактической границей, шаг `ended_by = operator`, сразу стартует следующий |
| Завершить партию | `POST /{id}/finish` | можно и посреди шага: шаг закрывается с `ended_by = finish` |
| Прервать | `POST /{id}/abort` | шаг `status = aborted`, партия `aborted` |

### Время

**Время показаний всегда считается от начала шага**, а не по часам сервера — поэтому партии,
запущенные в разное время, сравнимы между собой. `batch_step.started_at` / `finished_at` — реальные
моменты (UTC). `batch.finished_at` — конец процесса (конец последнего шага), а не момент нажатия
«Завершить», поэтому пауза оператора перед вводом качества не попадает в `t_total_sec`.

## 4. База данных

### Справочники (были до ТЗ)

| Таблица | Что хранит |
|---|---|
| `formula` | формула: `name`, `version` (пара уникальна) |
| `formula_steps` | шаги формулы: `step` (номер), `step_key` (уравнение), `in_data` / `out_data` (массы, кг), `dict_plc_id` (датчики шага и их диапазоны pre/during/post), `amount_time` (длительность шага), `constant` |
| `instruments` | приборы (в ТЗ — `device`) |
| `sensors` | датчики: `tag`, `parameter`, `unit`, `valid_min`/`valid_max` (физические пределы), `noise_sd` (шум) |

**Датчики шага** берутся из ключей `formula_steps.dict_plc_id`, а не через прибор, как в ТЗ:
так проект был устроен до ТЗ, и у шагов формулы 15 несколько датчиков разных приборов.

### Таблицы партий

**`batch`** — партия целиком (есть в дампе).

| Поле | Тип | Смысл |
|---|---|---|
| id | bigint | ключ |
| formula_id | bigint → formula | по какой формуле |
| status | varchar(16) | created / running / finished / aborted |
| started_at, finished_at | timestamptz | границы цикла (ограничение `chk_batch_status_dates` следит за согласованностью со статусом) |
| v_in | jsonb | сырьё по компонентам: `{"CaO": 62.5, "H20": 240}` |
| v_finish | numeric(14,4) | выход |
| quality | numeric(12,4) | качество |
| quality_unit | varchar(16) | `%` или единица концентрации (**добавляется init_db**) |
| is_reference | boolean | можно использовать как эталон |
| current_step | integer | текущий шаг; NULL — шаг не идёт |
| t_total_sec | time | длительность цикла (тип `time` из дампа — не больше суток) |

**`batch_step_window`** — усреднённые временные ряды (в ТЗ — `batch_step_metrics`, есть в дампе).

| Поле | Смысл |
|---|---|
| batch_id, step, time | первичный ключ; `time` — правая граница окна от начала шага (`00:00:02`, `00:00:04`, …) |
| detectors | jsonb, средние за окно: `{"D-LAC-04": 20.1, "M-GLU-WT": 298.8}` (в ТЗ — `V`) |
| n_samples | сколько показаний попало в средние (**добавляется init_db**) |

**`batch_step`** — таймер шагов (новая, создаётся `create_all`).

| Поле | Смысл |
|---|---|
| batch_id, step | первичный ключ |
| started_at, finished_at | от `started_at` отсчитывается время показаний шага |
| status | running / done / aborted |
| planned_seconds | плановая длительность из `formula_steps.amount_time` |
| ended_by | timer / operator / finish / abort |

**`batch_recommendations`** — история рекомендаций (новая).
`batch_id, step, time, tag, value` (среднее за окно), `ref_avg, ref_std, n_refs` (эталон),
`delta, threshold, message, created_at`.

### Как появляются новые таблицы и колонки

`init_db()` при старте сервера:
1. `Base.metadata.create_all` — создаёт **отсутствующие** таблицы (`batch_step`, `batch_recommendations`,
   таблицы модуля monitoring), существующие не трогает;
2. для PostgreSQL — `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` для `batch.quality_unit` и
   `batch_step_window.n_samples`, которых нет в дампе.

Всё идемпотентно: перезапуск сервера ничего не ломает.

### Данные в дампе

- Формула **15 «Мел»**: 3 шага по 10 секунд (`CaO + H20 → Ca(OH)2`, `Ca(OH)2 + CO2 → CaCO3 + H20`, `CaCO3`).
- **10 эталонных партий** (id 1–10) формулы 15: `status = finished`, `is_reference = true`,
  `quality = 94`, у каждой окна по 2 с на каждом шаге.

## 5. Эмулятор OPC (txt-файл с показаниями)

В MVP показания читаются не с OPC-сервера, а из txt-файла. Одна строка — одно показание:

```
# start=2026-10-20T10:00:00
# время;датчик;значение
2026-10-20T10:00:00.5;D-LAC-04;19.9251
2026-10-20T10:00:01;D-LAC-04;19.9381
2026-10-20T10:00:01;P-H2O-03;ERR
```

- Строки с `#` — комментарии. `# start=...` задаёт момент старта партии; без него стартом считается
  первая строка.
- Файл **проигрывается** с момента старта партии: строка «приходит», когда с начала прошло столько же
  секунд, сколько между ней и `start`. Параметр `speed` ускоряет это (и таймеры шагов) одинаково.
- Нечисловое значение (`ERR`, пусто) не ломает партию — считается в счётчик `bad_value`.
- Битая строка (не три поля, неразбираемое время) — ошибка `422` при старте с номером строки.

**По умолчанию** используется `data/opc_formula15.txt` (переменная `OPC_FILE`). Другой файл можно
указать при старте: `{"opc_file": "my_run.txt"}` — только из папки `data/`.

### Генератор файла

```bash
python scripts/make_opc_file.py                 # data/opc_formula15.txt
python scripts/make_opc_file.py --clean         # без намеренных отклонений и ERR
python scripts/make_opc_file.py --formula 15 --interval 0.5 --seed 15 --out data/x.txt
```

Читает эталонные партии **прямо из `sql/case_in.sql`** (БД не нужна). Значение датчика в окне =
среднее эталонов + шум (`noise_sd / 2`), обрезанное по физическим пределам датчика; показание каждые
0.5 с. Намеренные отклонения — список `DEVIATIONS` в начале скрипта:

| Шаг | Датчик | Окно | Множитель | Ожидаемая рекомендация |
|---|---|---|---|---|
| 1 | D-LAC-04 | 6 с | ×0.80 | увеличить массу лактида |
| 2 | CI-FT-01 | 8 с | ×1.45 | уменьшить расход |

## 6. Усреднение по окнам

- Окно — полуинтервал **(end − window; end]**: показание ровно на 2.0 с попадает в окно `time = 2.0`.
- Размер окна — `window_seconds` при старте, по умолчанию **2 с** (4 показания × 0.5 с, как в ТЗ и в эталонах дампа).
- Окно закрывается, когда время шага ушло за его правую границу. Пустые окна не записываются.
- Последнее окно шага обрезается концом шага; если шаг закончил оператор, `time` = фактическая граница
  (например, `3.239`).
- **В средние не попадают:**
  - датчики, которых нет в `dict_plc_id` текущего шага (`ignored`);
  - нечисловые значения (`bad_value`);
  - значения вне `sensors.valid_min / valid_max` — это сбой датчика, а не процесс (`out_of_range`).

Счётчики видны в `GET /api/batches/{id}` → `live.readings`.

## 7. Сравнение с эталоном и рекомендации

При старте партии (`repo.load_references`):

1. **Кандидаты** — партии той же формулы с `is_reference = true` и `status = finished`
   (до 100 последних; опционально `quality >= min_ref_quality`).
2. **Выбор 10** (`ref_limit`) — сначала ближайшие по `v_in`, при равенстве — более свежие.
   Расстояние по `v_in` — средняя относительная разница по компонентам сырья (компонент есть только
   у одной партии → 1).
3. Окна выбранных партий загружаются в память один раз на всю партию.

На каждом закрытом окне (`reference.compare`), для каждого датчика:

```
значения эталонов на этом шаге и в это же время окна  →  ref_avg, ref_std (выборочное)
delta     = текущее среднее − ref_avg
threshold = max(k · ref_std, допуск датчика)        k = 3 (параметр k), допуск = sensors.noise_sd
|delta| > threshold  →  рекомендация
```

Текст строится функцией `monitoring.engine.action_message` (та же, что в симуляции):
глагол по знаку `delta` (повысить/понизить для температуры, давления, pH…; увеличить/уменьшить —
для остального), целевое значение — `ref_avg`.

Если у эталонов нет окна на это время (шаг закончен досрочно, окно другой длины) — окно не сравнивается.

> ⚠️ **Качество эталонов решает всё.** Партия с аномалией, помеченная эталонной, раздувает `ref_std`,
> и порог перестаёт ловить отклонения. Помечайте эталонными только действительно хорошие партии.

## 8. API

Все ответы — JSON. Ошибки: `404` — не найдено, `409` — действие не подходит к статусу партии,
`422` — неверные данные (текст в `detail`).

### Партии `/api/batches`

| Метод | Путь | Тело / параметры | Что делает |
|---|---|---|---|
| POST | `/api/batches` | `{"formula_id": 15, "v_in": {...}?}` | создать партию |
| GET | `/api/batches` | `?formula_id=15&only_reference=true` | последние 100 партий |
| GET | `/api/batches/{id}` | | партия + шаги + `live` (если показания сейчас принимаются) |
| PUT | `/api/batches/{id}/v_in` | `{"v_in": {"CaO": 62.5, "H20": 240}}` | ввести сырьё (только `created`) |
| POST | `/api/batches/{id}/start` | см. ниже | запуск |
| POST | `/api/batches/{id}/next-step` | | закончить текущий шаг досрочно |
| POST | `/api/batches/{id}/finish` | `{"v_finish": 100.5, "quality": 94, "quality_unit": "%", "is_reference": false}` | завершить |
| POST | `/api/batches/{id}/abort` | | прервать |
| PUT | `/api/batches/{id}/reference` | `{"is_reference": true}` | пометить эталонной (только `finished`) |
| GET | `/api/batches/{id}/metrics` | `?step=1` | окна: `[{step, time_s, V, n_samples}]` |
| GET | `/api/batches/{id}/recommendations` | `?step=1&after_id=0` | рекомендации; `after_id` — подгружать только новые |

Параметры старта (все необязательные):

| Поле | По умолчанию | Смысл |
|---|---|---|
| `speed` | 1 | ускорение времени (1–100) |
| `window_seconds` | 2 | окно усреднения |
| `k` | 3 | множитель разброса в пороге |
| `ref_limit` | 10 | сколько эталонных партий сравнивать |
| `min_ref_quality` | — | эталоны только с `quality >=` |
| `opc_file` | `opc_formula15.txt` | файл показаний из `data/` |

### Пример через curl

```bash
A=localhost:8000/api/batches; H='content-type: application/json'
curl -s -XPOST $A -H "$H" -d '{"formula_id":15,"v_in":{"CaO":62.5,"H20":240}}'      # → {"id": 11, ...}
curl -s -XPOST $A/11/start -H "$H" -d '{"speed":10}'
curl -s $A/11                                    # live.step, live.step_elapsed_s, live.recommendations
curl -s $A/11/recommendations
curl -s -XPOST $A/11/finish -H "$H" -d '{"v_finish":100.5,"quality":94}'
```

### Остальное

| Префикс | Что |
|---|---|
| `/api/formulas` | создать формулу (`POST`), список, формула с шагами, `POST /{id}/calculate` — расчёт массы продукта |
| `/api/sensors` | список датчиков |
| `/api/simulation` | симуляция по стадиям — раздел 12 |

## 11. Принятые решения и ограничения

### Вопросы из ТЗ (раздел 7) — как решены сейчас

| Вопрос | Решение | Где поменять |
|---|---|---|
| Окно усреднения | 2 с, общее для всех датчиков шага | `window_seconds` при старте |
| Завершение шага | по `amount_time` формулы **или** кнопкой оператора; шаг без `amount_time` ждёт оператора | `process.py` |
| «Приоритет массы сырья» | подбор эталонов по близости `v_in`; нормировки показаний на объём нет | `reference.v_in_distance` |
| Статус эталона | вручную: флаг при завершении или `PUT /reference` | — |
| Шаги разной длины | сравниваются только окна с тем же временем | `RefIndex.at` |

### Отличия от текста ТЗ

- `batch_step_metrics` → существующая `batch_step_window`, поле `V` → `detectors`.
- `step_no` → `step` (как во всех таблицах проекта).
- `v_in` — словарь по компонентам сырья, а не одно число (так в дампе).
- Нет `device_id` в шаге и `interval_ms` у датчика: датчики шага — из `dict_plc_id`.
- Шаблоны текстов рекомендаций не вынесены в БД — текст строит `action_message`.

### Известные ограничения

- **Досрочный переход сдвигает данные.** Файл эмулятора — один непрерывный поток на всю партию.
  Если оператор закончил шаг раньше, показания следующего шага придут позже его старта, и окна разойдутся
  с эталоном по времени (такие окна просто не сравниваются).
- **`speed` и длительность.** `t_total_sec` и `started_at`/`finished_at` — реальное время: при `speed = 10`
  30-секундная партия длится 3 с.
- **Перезапуск сервера.** Приём показаний живёт в памяти процесса. После перезапуска идущие партии
  остаются `running` без приёма показаний — их можно завершить или прервать.
- **Одна партия ≠ один процесс сервера.** Несколько партий одновременно работают, но при нескольких
  воркерах uvicorn управлять партией надо через тот же процесс, где она запущена. Запускайте с одним воркером.
- **`t_total_sec`** в дампе имеет тип `time` — партия дольше суток не запишется (вернётся `422`).
- **Единицы `amount_time`.** `POST /api/formulas` принимает `amount_time` в **минутах**, а партия
  читает интервал как есть. У формулы 15 в дампе — 10 секунд.

## 12. Симуляция (модуль monitoring)

Отдельный, более ранний механизм: прогон формулы по стадиям с проверкой каждого показания
по допустимым диапазонам `dict_plc_id` (pre / during / post) и синтетическим эталонам.
Пишет в свои таблицы `sim_runs`, `sim_step_runs`, `sensor_readings`, `sensor_alerts`,
`reference_batch_values` и с партиями не пересекается.

| Метод | Путь | Что |
|---|---|---|
| POST | `/api/simulation/reference/generate` | сгенерировать эталонные партии для формулы |
| GET | `/api/simulation/reference/{fid}` | средние эталонов и допустимые полосы |
| PATCH | `/api/simulation/formulas/{fid}/steps/{step}/duration` | длительность стадии, секунд |
| POST | `/api/simulation/start` | запустить (одна симуляция за раз) |
| POST | `/api/simulation/stop` | остановить |
| GET | `/api/simulation/status` | ход и последние сигналы |
| GET | `/api/simulation/runs`, `/runs/{id}/steps`, `/runs/{id}/readings`, `/runs/{id}/alerts` | результаты |

Источник показаний — `data/sensor_data_5000.csv` или генератор (`source`: auto / file / synthetic).
